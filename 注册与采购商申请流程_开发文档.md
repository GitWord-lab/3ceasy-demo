# 注册与采购商申请流程开发文档

## 1. 项目目标

当前注册流程存在以下问题：

1. 用户仅通过 Email 注册，缺少电话信息，客服无法进行电话跟进。
2. 普通客户需要主动进入 User Profile 才能发现 Tax Exemption 入口。
3. 零售客户与企业采购客户走同一条路径，容易增加零售用户的操作负担。
4. Customer → Buyer 的角色转换逻辑较简单，缺少“申请中 / 审核中 / 已通过”等状态。
5. 客服无法清晰识别哪些客户具有明显的批发采购意向。

### 产品目标

在不明显增加零售客户注册成本的情况下：

- 收集基础电话信息。
- 尽早识别 Retail / Business 购物意图。
- 让 Business Customer 能够在注册后快速进入 Tax / Wholesale 申请。
- 保留零售客户直接购物的顺畅体验。
- 建立完整的 Wholesale Application 状态体系。
- 为客服提供可跟进的电话、公司、申请状态和客户行为信息。

## 2. 新整体流程

```text
Register Account
      |
      v
Basic Account Information
(Email / Password / Name / Phone)
      |
      v
How will you use your account?
      |
      +----------------------------+
      |                            |
      v                            v
I’m shopping for myself      I’m purchasing for my business
      |                            |
      v                            v
Retail Customer              Wholesale Application
      |                            |
      v                            v
Shopping                     Business Information
                                   |
                                   v
                              Tax Document
                                   |
                                   v
                            Submit Application
                                   |
                                   v
                              Under Review
                                   |
                            +------+------+
                            |             |
                            v             v
                         Approved      More Info / Rejected
                            |
                            v
                  Retail + Wholesale Price
```

核心原则：

> Account Registration 与 Wholesale Application 分离。所有人先拥有账户，只有有企业采购需求的客户才进入复杂的 Tax / Wholesale 流程。

# 3. 用户身份模型

建议不要只使用简单的 `Customer / Buyer` 两个角色，而使用“账户 + 申请状态 + 价格权限”三个维度。

## 3.1 Account

所有注册用户都有 Account。

基础字段：

- Email
- Password
- First Name
- Last Name
- Phone Number
- Account Created At

## 3.2 Customer Type

建议：

- `RETAIL`
- `BUSINESS`

注意：Business 表示采购意图，不代表已经获得批发价权限。

## 3.3 Wholesale Application Status

建议：

- `NOT_STARTED`
- `DRAFT`
- `SUBMITTED`
- `UNDER_REVIEW`
- `MORE_INFO_REQUIRED`
- `APPROVED`
- `REJECTED`

## 3.4 Pricing Access

建议单独由权限控制：

- `RETAIL_ONLY`
- `RETAIL_AND_WHOLESALE`

不要直接用“Buyer 角色 = 批发价”硬编码，避免以后扩展 Dealer / Distributor / VIP 等价格体系时需要重构。

# 4. 注册流程

## 4.1 Registration Page

### 必填字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| Email | string | 是 | 登录账号 |
| Password | password | 是 | 登录密码 |
| First Name | string | 是 | 名 |
| Last Name | string | 是 | 姓 |
| Phone Number | string | 是 | 联系电话 |

### Phone UX

电话应该在注册阶段收集，而不是等 Wholesale Application 时才收集。

建议：

- 支持国家码。
- 前端做基础手机号格式校验。
- 后端保存标准化号码。
- 不要在注册页面使用“Wholesale Phone”之类的文案。

推荐辅助文案：

> We may use your phone number to contact you regarding your orders or account.

目的：让零售客户理解电话是账户基础信息，不会认为自己正在申请批发账户。

# 6. Retail Customer 流程

用户选择：

`I’m shopping for myself`

系统执行：

```text
customer_type = RETAIL
wholesale_application_status = NOT_STARTED
pricing_access = RETAIL_ONLY
```

用户直接进入网站购物。

不要要求用户填写：

- Company Name
- Tax ID
- Tax Exemption Document
- Business Type

### Retail 用户账户页

建议显示：

**Account Information**

- Name
- Email
- Phone

同时提供一个非强制入口：

### Unlock Wholesale Pricing

> Purchasing for a business? Submit your tax exemption information to apply for wholesale pricing.

按钮：

**Apply for Wholesale Pricing**

这样零售用户可以完全忽略，不影响正常购物；有企业采购需求的用户可以主动进入申请流程。

---

# 7. Wholesale Application 流程

用户选择：

`I’m purchasing for my business`

进入 Wholesale Application。

## Step 1 — Business Information

建议字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| Company Name | string | 是 | 企业名称 |
| Business Type | select | 是 | 企业类型 |
| Business Phone | string | 否 | 默认使用账户 Phone，可修改 |
| Tax ID | string | 视业务规则 | 税务编号 |
| Website | string | 否 | 企业网站 |
| Business Address | address | 视业务规则 | 企业地址 |

注意：

如果账户已经有 Phone，则默认带入，不要让用户再次输入。

---

# 8. Tax Exemption Document

## Upload

字段：

`tax_exemption_document`

建议支持：

- PDF
- JPG / JPEG
- PNG

### 前端限制

建议限制：

- 单文件大小，例如 10MB
- 文件类型白名单
- 文件上传成功后显示文件名
- 支持替换文件
- 提交前必须确认文件已成功上传

### 页面文案

**Tax Exemption Document**

> Upload your valid tax exemption or resale certificate.

如果不同州 / 国家存在不同文件要求，应由业务配置，不要把规则硬编码在前端。

**Application Submitted**

# 10. 审核状态

## 10.1 Not Started

表示用户还没有开始 Wholesale Application。

CTA：

**Apply for Wholesale Pricing**

## 10.2 Draft

表示用户开始填写但没有提交。

CTA：

**Continue Application**

## 10.3 Submitted

表示已提交。

CTA：

**View Application**

## 10.4 Under Review

表示客服 / 后台正在审核。

前台文案：

> Your wholesale application is currently under review.

## 10.5 More Info Required

如果资料不足：

> We need additional information to complete your application.

CTA：

**Update Application**

## 10.6 Approved

审批通过：

```text
wholesale_application_status = APPROVED
pricing_access = RETAIL_AND_WHOLESALE
```

显示：

> Your wholesale account has been approved.

## 10.7 Rejected

前台显示申请未通过，并允许用户查看原因或联系支持团队。

# 11. 价格权限逻辑

不要直接根据 Customer Type 决定价格。

建议：

```text
if pricing_access == RETAIL_ONLY:
    show retail price

if pricing_access == RETAIL_AND_WHOLESALE:
    show retail price
    show wholesale price
```

### 重要安全要求

价格权限必须由后端决定，不能只依赖前端隐藏价格。

后端 API 返回商品价格时必须根据当前用户权限进行过滤。

禁止通过修改前端请求参数直接获取未授权 Wholesale Price。

# 15. 审核操作

管理员至少需要：

- Approve
- Request More Information
- Reject

## Approve

执行：

```text
application_status = APPROVED
pricing_access = RETAIL_AND_WHOLESALE
```

## Request More Information

执行：

```text
application_status = MORE_INFO_REQUIRED
```

同时要求管理员填写备注。

## Reject

执行：

```text
application_status = REJECTED
pricing_access = RETAIL_ONLY
```

必须填写拒绝原因。

# 16. 电话信息要求

这是本次改版的重要需求。

## Registration

Phone 必填。

## Wholesale Application

Business Phone 默认读取 Account Phone。

用户可以修改，但是不要重复强制输入。

### 建议数据结构

```text

business.phone
```

这样：

- Account Phone = 用户日常联系号码
- Business Phone = 企业业务联系号码

两者可以暂时相同。

# 23. 异常场景

开发时必须处理以下情况。

## 用户关闭页面

如果用户已经开始填写但没有提交，应保存 Draft。

下次进入账户可以：

**Continue Application**

## Tax 文件上传失败

显示明确错误：

> Upload failed. Please try again.

不能导致整份申请数据丢失。

## 重复提交

用户连续点击 Submit 不得生成多个 Application。

## 审核期间修改资料

推荐：

- Under Review 时限制关键字段修改。
- 如果允许修改，修改后自动重新进入审核队列。

## 已 Approved 的用户再次申请

禁止创建重复申请，除非业务需要重新审核。

# 24. UX 要点

整个改版最重要的是不要让零售客户感觉：

> “我为什么必须填写这么多企业资料？”

所以设计上要做到：

### Retail

```text
注册
↓
输入基本信息
↓
选择 Shopping for myself
↓
直接购物
```

### Business

```text
注册
↓
输入基本信息
↓
选择 Purchasing for my business
↓
填写 Business Info
↓
上传 Tax Document
↓
提交
↓
审核
```

复杂信息只在真正需要的时候展示。

# 25. 第一阶段 MVP

如果希望降低开发成本，可以第一阶段只实现：

1. 注册增加 Phone。
2. 注册完成后增加 Retail / Business 选择。
3. Business 增加 Wholesale Application。
4. 增加 Tax Document Upload。
5. 增加 Application Status。
6. 后台增加 Approve / Reject / Request More Info。
7. Approved 后开放 Wholesale Price。
8. Account 页面增加 Wholesale Application 状态。

暂时可以不做：

- Lead Score
- 高级 CRM 集成
- 复杂自动化营销
- 多级 Dealer / Distributor Pricing

# 28. 最终推荐产品结构

```text
ACCOUNT
│
├── Basic Information
│   ├── Email
│   ├── Password
│   ├── Name
│   └── Phone
│
├── Customer Intent
│   ├── Retail
│   └── Business
│
└── Wholesale Application
    ├── Business Information
    ├── Tax Information
    ├── Tax Document
    ├── Application Status
    └── Review History

PRICING ACCESS
│
├── Retail Only
└── Retail + Wholesale
```

## 结论

本次改版不建议把所有注册用户都直接变成 Wholesale Applicant，也不建议注册阶段强制所有人填写 Tax 文件。

最优的产品逻辑是：

> **所有用户先完成轻量账户注册；零售客户直接购物；企业采购客户在注册后被明确引导进入 Wholesale Application；电话作为所有账户的基础信息提前收集；Tax 文件仅对企业采购用户要求；审核通过后单独授予 Wholesale Pricing 权限。**

这样既降低零售客户的注册阻力，也能显著改善企业客户的转化、客服跟进和后台管理。
